# Кварта — лендинг обжарки кофе

Тестовое задание: лендинг небольшой обжарки в Минске с работающей формой заявки.
Клиент вымышленный, факты — из брифа.

**Стек:** Next.js 15 (App Router, TypeScript, Tailwind 4) · Express · PostgreSQL

## Как запустить локально

Нужен Node 20+ (разрабатывалось на 24–26).

```bash
npm install
npm run dev
```

Одна команда поднимает всё:

- **локальный Postgres** на `:5433` — embedded-postgres: бинарники PostgreSQL
  приходят npm-пакетом во временный каталог, ставить СУБД на машину не нужно;
- **API (Express)** на `:4001`;
- **фронтенд (Next)** на `:3000` — http://localhost:3000

Строка подключения по умолчанию уже рабочая (`postgres://kvarta:kvarta@localhost:5433/kvarta`).
Для прод-базы скопируйте `.env.example` в `backend/.env` и подставьте свой
`DATABASE_URL` — подойдёт бесплатная облачная (например, Neon).

## Как устроено

- **frontend** — лендинг. Все вызовы API идут на собственный origin `/api/*`,
  Next проксирует их на Express (rewrites в `next.config.ts`): браузеру не нужен
  адрес бэкенда, CORS не нужен, при деплое адрес API меняется одной переменной.
- **backend** — Express: приём заявок `POST /api/lead`, публичные данные для
  лендинга `GET /api/products` и `GET /api/settings` и закрытая админка
  `/api/admin/*`. Схема (`leads`, `products`, `subscriptions`, `settings`,
  `admin_users`) создаётся при старте — для объёма задачи миграции избыточны.

## Решения по заданию

- **Хранение заявок — PostgreSQL.** Менеджеру нужны выборки и фильтры по
  источникам, поэтому файл-CSV отпадает сразу; SQLite плохо живёт на бесплатных
  serverless-хостингах (эфемерная файловая система). Postgres есть бесплатным
  у Neon/Supabase, подключение — строкой в переменной окружения.
- **Дедупликация 10 минут.** Телефон нормализуется к `+375XXXXXXXXX`
  (понимаем `8 029…`, `8029…`, `37529…`, `2912…`), дальше в транзакции:
  advisory-лок по хэшу телефона → проверка «была ли заявка с номера за 10 минут»
  → вставка. Двойной клик и повторная отправка второй строки не создают,
  человек получает аккуратный ответ «заявка уже у нас».
- **Валидация телефона.** Белорусские мобильные коды 25/29/33/44; городские
  не принимаем — форма под обратный звонок. Алгоритм одинаковый на клиенте и
  сервере, подсказка показывает нужный формат.
- **Атрибуция для менеджера.** При входе на сайт снимаем `utm_*` (первый
  источник в сессии — главный, при переходах по сайту не перетирается),
  referrer и адрес страницы; всё уходит в заявку.
- **Источник заявки.** По UTM и referrer определяем рекламный источник —
  сейчас это Instagram и Яндекс (реклама идёт в основном туда). Пометка видна
  в админке и уходит в Telegram; заявки мимо этих двух — без метки.
- **Админка `/admin`.** Вход по логину и паролю (JWT в httpOnly-куке, на
  попытки входа — rate limit). Заявки делятся по типам, выполненные
  складываются отдельно; из заявки на подписку одним нажатием оформляется
  действующая подписка (с паузой и отменой, можно добавить и вручную — по
  телефону). Каталог зёрен и условия подписки редактируются тут же, лендинг
  берёт их из базы.
- **Состояния формы.** «Отправляем…», успех, дубль, ошибка валидации, ошибка
  сети — при любой неудаче человек видит, что случилось, и телефон, по которому
  можно позвонить.
- **Бонусы.** Релей заявки в Telegram: в админке («Настройки») указывается
  числовой id получателя — бот пишет заявки в личку; там же инструкция и
  кнопка тестового сообщения. Нужен `TELEGRAM_BOT_TOKEN` в `backend/.env`.
  OG-превью для мессенджеров, лёгкие CSS-анимации.
- **Иллюстрации-чашки.** Рисованная SVG-чашка с паром в трёх местах:
  карточка подписки (покачивается), блок заявки и подвал. Анимация чистым
  CSS: ноль килобайт картинок и библиотек, при `prefers-reduced-motion`
  замирает.
- **Производительность.** Фото пережаты в webp (3,2 МБ исходников → ~300 КБ),
  шрифты self-hosted через next/font, стартовый JS — ~111 КБ, страница
  пререндерена статикой; семантическая вёрстка и адаптив от 360px.

## Замечания о локальной базе

На Windows, если проект лежит в пути с кириллицей (например, OneDrive
«Рабочий стол»), initdb не поднимает кластер в UTF-8 — поэтому локальный
кластер создаётся в системной кодировке, а клиент pg общается с сервером
в UTF-8 (`client_encoding` в `backend/src/db.ts`): конвертация происходит
на уровне протокола. Эмодзи в комментариях на локальной cp1251-базе не
сохранятся — на проде с UTF-8-базой ограничения нет.

## Где ИИ ошибся, и как я это заметил

Черновик по фактам сессии (пересказать своими словами):

- ИИ забыл добавить сам пакет `embedded-postgres` в зависимости, хотя скрипт
  базы уже был написан, — увидел по `ERR_MODULE_NOT_FOUND` при первом запуске.
- Первый вариант локальной базы падал: initdb с UTF-8 не поднимается, когда
  путь проекта содержит кириллицу; ИИ сначала попытался лечить флагами,
  финальное решение — системная кодировка кластера + `client_encoding=utf8`
  у клиента.
- Проверяя форму curl'ом из консоли Windows, получил необъяснимую ошибку
  вставки: консоль перекодировала кириллицу в аргументах, в JSON попадали
  U+FFFD. Через файл с UTF-8 всё заработало — то есть баг был в способе
  тестирования, а не в бэкенде.
- Фронтенд не собирался: ИИ не экспортировал тип `Interest` из модуля формы,
  который импортировала кнопка на карточке, — TypeScript указал на файл
  и строку.
